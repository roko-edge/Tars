# Memory Files

The NPU prototype uses hexadecimal text files accepted by SystemVerilog
`$readmemh`. There is no versioned or stable interchange format between Rust and
SystemVerilog.

## `activations.mem`

`npu/tb.sv` loads this file directly into the DUT's signed 32-bit activation array:

```systemverilog
$readmemh("activations.mem", dut.act);
```

The checked-in file contains four 32-bit hexadecimal words:

```text
00000001
00000002
00000003
00000004
```

The NPU interprets these values as signed integers.

## `weights.mem`

The Rust training executable overwrites this file after training. For every `Linear`
module, it writes weights in output-neuron-major order:

```rust
writeln!(file, "{:08X}", weight.to_bits())?;
```

Each line therefore represents the raw IEEE-754 binary32 bit pattern of one `f32`.
The file contains no header, dimensions, biases, activation identifiers, or numeric
format marker.

The SystemVerilog testbench loads the same lines directly into a signed 32-bit integer
array:

```systemverilog
$readmemh("weights.mem", dut.weights);
```

No IEEE-754 decoding occurs in the NPU. A Rust value such as `1.0`, written as
`3F800000`, is consumed as the signed integer `1065353216` rather than as a floating-
point value.

## Size requirements

The testbench instantiates the NPU with `N = 4`; both memory arrays therefore require
four initialized words for a complete dot product. The checked-in
`activations.mem` has four words, while the checked-in `weights.mem` currently has
two. Uninitialized array entries can propagate unknown values through the simulation.

The number of weights emitted by Rust depends on the selected model:

| Experiment | Model | Exported weights |
|---|---|---:|
| OR | `2 -> 1` | 2 |
| XOR | `2 -> 4 -> 1` | 12 |

Neither output size matches the four-element vector expected by the current
testbench without selecting and arranging a subset externally.

## Current limitations

- Rust and SystemVerilog do not share a numeric encoding.
- Bias values are not exported.
- Model topology and activation functions are not exported.
- Input and expected-output files are not generated by Rust.
- The testbench does not validate file length or simulation output.
- The files do not include a format version or compatibility marker.
